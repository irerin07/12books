# 설계 전제 점검: 복잡성의 원인부터 줄이기

## 목적과 범위

이 문서는 코드를 짧게 만드는 일반적인 리팩터링 목록이 아니다. 다음 패턴을 찾아 정리한 설계 검토다.

> 불필요하거나 재검토가 필요한 설계 전제를 고정한 채, 그 전제가 만든 문제를 국소적으로 보수하면서 복잡성을 늘리는 것.

대표 사례는 댓글 수다. 댓글 수를 컬럼에 저장하기로 하면서 작성·삭제·운영자 숨김·복구·회원탈퇴 때마다 숫자를 보정해야 했다. 이 경우 개별 보정 코드를 고치는 것보다, 숫자를 별도로 저장해야 하는지 먼저 판단해야 한다.

- 대상: 이번에 연속 검토한 `book`, `feed`, `follow`, `notification`, `post`, `reading`, `report`, `user` 패키지와 직접 연결된 코드.
- 기준 커밋: `4d44d0515d4b6f894eddcdfeeec284684476042f`.
- 검증 수준: 소스·설정·마이그레이션·관련 테스트를 읽은 정적 검토. 이번 검토에서 테스트 실행, 부하 측정, 동시성 재현은 하지 않았다.
- 이전 auth 검토는 이 문서에서 재검증하지 않았으므로 별도 범위로 남긴다.
- 아래 제안은 구현 승인이나 정책 변경의 확정이 아니다. 기존 데이터 삭제, 마이그레이션 수정, 보안 보장 축소를 자동으로 허용하지 않는다.

### 항목 구분

| 구분 | 의미 |
|---|---|
| 오류 경로 | 현재 코드에서 잘못된 결과가 나오는 순서를 설명할 수 있음. 실행 재현 완료를 뜻하지는 않음 |
| 단순화 후보 | 같은 요구를 더 적은 처리로 만족시킬 대안. 실제 변경 전에 동작·비용 비교 필요 |
| 정책 결정 | 사용자가 경험하는 동작이나 데이터 보존 범위를 바꾸므로 제품 판단이 먼저 필요 |

## 핵심 결론

1. 댓글·좋아요의 저장된 카운터가 여러 패키지의 잠금과 보정 절차를 만들었다.
2. 신고에 대한 판단과 콘텐츠 공개 여부를 결합하면서 여러 신고 간 정합성 문제가 생겼다.
3. 독서 기록은 회차별 보존 모델로 바뀌었지만, 일부 상태 변경과 집계는 과거의 단일 상태 모델을 유지한다.
4. 탈퇴 데이터 보존과 알림 실패 격리는 큰 비용을 수반하는 정책이다. 개별 예외 처리에 앞서 그 비용을 받아들일 이유를 확인해야 한다.
5. 모든 패키지가 과잉 설계인 것은 아니다. 필요한 검증·잠금·유니크 제약까지 일괄 제거하면 안 된다.

## 1. 반응 수를 저장하면서 생긴 보정 체계

**대상:** `post`, `report`, `user` / **구분:** 단순화 후보, 일부 오류 경로

### 현재 구조

댓글과 좋아요 원본 행 외에 `posts.comment_count`, `posts.like_count`도 저장한다. 같은 사실을 두 곳에 유지하므로 다음 처리가 필요해졌다.

- 반응 생성 전에 글의 카운터를 증가시키며 부모 행 잠금.
- 취소·삭제 시 실제 변경된 행 수에 따라 감소.
- 숨김·복구 시 현재 카운터에 포함된 댓글과 그렇지 않은 댓글을 구분.
- 숨겨진 부모 글에도 적용되는 운영자 전용 카운터 갱신.
- 탈퇴 시 사용자가 작성한 댓글을 글별로 집계해 기존 숫자에서 차감.

`ReportAdminService.onComment()`의 세 함수 인자는 이 보정 절차를 추상화한 것이다. 함수 이름이나 클래스 분리만 고쳐서는 원인이 없어지지 않는다.

### 영향

같은 글에 대한 독립적인 댓글·좋아요가 같은 부모 행의 배타 잠금을 기다린다. 또한 `UserService.withdraw()`는 탈퇴 표시를 먼저 커밋한 후 댓글 수를 보정하고 refresh 세션을 정리한다. 보정이 실패하면 세션 정리에 도달하지 못하고, 재요청은 이미 탈퇴한 계정이라는 이유로 거부될 수 있다.

단, refresh 재발급에는 별도 탈퇴 검사가 있다. 세션 정리 미완료가 곧 재발급 허용이라는 뜻은 아니다.

### 권장 방향

페이지에 포함된 글 ID를 대상으로 댓글·좋아요를 묶어서 집계하는 방식을 비교한다. 글마다 COUNT를 호출하는 N+1 방식으로 바꾸자는 뜻이 아니다. 댓글 집계는 삭제·숨김·작성자 탈퇴 등 실제 노출 기준과 맞춰야 한다.

카운터를 제거한다면 관련 보정 메서드와 호출 경로를 함께 제거한다. 다만 권한 검사, 반응 중복 방지, 삭제·숨김과 생성의 경쟁 정책까지 제거하지 않는다. 읽기 집계 비용은 실제 데이터로 확인해야 한다.

**근거 코드:** `post/PostLikeService.java`, `post/CommentService.java`, `post/PostRepository.java`, `post/CommentRepository.java`, `report/ReportAdminService.java`, `user/UserService.java`.

## 2. 신고 기각과 콘텐츠 복구의 결합

**대상:** `report` / **구분:** 정책 결정 + 오류 경로

현재 `ACTIONED`는 숨김, `REJECTED`는 다른 인정된 신고가 없을 때 복구를 수행한다. 하지만 “이 신고의 주장은 타당하지 않다”와 “콘텐츠를 다시 공개한다”는 별개의 판단이다.

둘을 결합하면서 `existsOtherWithStatus()`로 다른 신고를 조회하고, 여러 신고 상태와 콘텐츠의 `hiddenAt`을 일치시켜야 한다.

### 현재 가능한 실패 순서

같은 글에 인정된 신고 A와 B가 있을 때:

1. A 기각 요청이 아직 인정 상태인 B를 보고 복구하지 않는다.
2. B 기각 요청도 아직 인정 상태인 A를 보고 복구하지 않는다.
3. 각각 자기 신고를 기각으로 저장한다.
4. 인정된 신고는 없지만 콘텐츠는 숨겨진 채 남는다.

이 순서는 콘텐츠 UPDATE 이전에 복구를 포기하므로 기존 콘텐츠 잠금만으로 막히지 않는다.

### 결정할 것

신고 결과 기록과 콘텐츠 숨김·복구 명령을 분리할지 결정한다. 화면에서는 한 번의 작업으로 함께 요청할 수 있지만, 기각의 암묵적 부수 효과로 복구하지 않도록 하는 방향이다.

반대로 “인정된 신고가 하나라도 있으면 반드시 숨긴다”가 요구라면 결합을 유지하고 대상 단위 동시성 제어를 설계해야 한다. 기존 정책을 유지하는 동안에는 위 오류를 방치하면 안 된다.

**근거 코드:** `report/ReportAdminService.java`의 `handle`, `restore`; `report/ReportRepository.java`의 `existsOtherWithStatus`.

## 3. 독서 회차와 현재 서재 상태의 혼합

**대상:** `reading` / **구분:** 정책 결정 + 오류 경로

### 3-1. 재독 경로에 따라 과거 기록 보존이 달라진다

- 서재에서 빼고 `resume=false`로 다시 담으면 새 행을 만들고 이전 기록을 보존한다.
- 기존 기록을 `FINISHED → READING`으로 바꾸면 같은 행의 완독일을 지운다. 코드 설명은 이를 재독 시작이라고 부른다.

전자는 회차별 기록, 후자는 책마다 현재 상태 하나를 유지하던 모델이다. 상태 정정과 새 회차 시작을 구분해야 한다. 단순히 완독일을 지우지 않게 바꾸면 다른 모순이 생긴다.

### 3-2. 과거 기록을 남기면서 완독 수에서는 제외한다

`countFinishedBetween()`은 `inBookshelf = true`인 기록만 센다. 따라서 완독한 책을 서재에서 빼면 기록은 남아도 연간 목표의 완독 수에서 빠진다.

서재 전시 여부와 독서 실적의 집계 기준을 분리할지 결정해야 한다. 그 전에 재독 두 회를 2회로 셀지, 서로 다른 책 한 권으로 셀지도 명확히 해야 한다.

### 3-3. 최종 값 검증 전에 중간 상태를 보정한다

`Reading.apply()`는 `changeStatus()`로 기존 총 쪽수를 기준으로 진도를 보정한 뒤, `applyProgress()`로 새 값을 검증한다.

예: 기존 `READING, 총 300쪽, 현재 100쪽`에 `FINISHED, 총 200쪽, 현재 쪽수 생략`을 적용하면, 중간에 현재 쪽수가 300이 되어 `300 > 200` 검증에 걸린다. 최종 규칙으로는 `FINISHED, 200/200`으로 정리할 수 있는 요청이다.

최종 후보 값을 먼저 계산하고 검증·보정한 뒤 한 번에 반영하는 방향이 명확하다. 명시적으로 잘못 입력한 진도를 거부할지 보정할지는 별도로 일관되게 정해야 한다.

**근거 코드:** `reading/Reading.java`의 `changeStatus`, `apply`, `applyProgress`; `reading/ReadingService.java`의 `add`; `reading/ReadingRepository.java`의 `countFinishedBetween`; `reading/ReadingSessionTest.java`.

## 4. 글 작성이 서재를 자동으로 변경하는 전제

**대상:** `post`, `reading` / **구분:** 정책 결정

“서재에 담지 않아도 글을 쓸 수 있다”와 “글을 쓰면 자동으로 서재에 담긴다”는 다른 요구다.

현재 `ReadingLinker`는 기록 탐색, 과거 기록 재담기, 별도 트랜잭션 생성, 중복 생성 복구, 잠금까지 수행한다. `Post` 자체에는 이미 작성자·책·본문·읽은 구간이 있다.

검토한 백엔드에서 `readingId`는 연결·저장·응답에 사용되지만 이를 조건으로 글을 조회하는 경로는 확인되지 않았다. 클라이언트 사용 여부까지 확인한 것은 아니다.

자동 담기와 특정 회차 연결의 필요성을 각각 확인한다. 요구라면 유지하되, 불필요하다면 일부 잠금이 아니라 글 작성의 서재 변경 흐름 전체를 제거 후보로 삼는다.

추가로, 서재 빼기는 현재 행 삭제가 아니라 `inBookshelf` 변경이다. 물리 삭제에 의한 FK 실패를 설명하는 `ReadingLinker` 주석은 현재 경로와 맞지 않는다. 재담기 경쟁은 남으므로 잠금을 전부 제거할 근거는 아니다.

## 5. 알림 실패 격리의 비용과 중복 저장 처리

**대상:** `notification` / **구분:** 정책 결정 + 단순화 후보

### 5-1. 같은 DB의 알림 INSERT도 독립적으로 실패해야 하는가

현재 구조는 다음 선택의 연쇄다.

> 알림 실패가 본 기능을 롤백시키면 안 됨 → 커밋 후 독립 트랜잭션 → 추가 커넥션 경합 → 비동기 실행 → 유한 대기열 → 포화 시 폐기 → 폐기 메트릭과 로그 집계

실패 격리는 계획에 명시돼 있다. 따라서 비동기를 임의로 제거할 수는 없다. 다만 현재 알림은 외부 발송이 아니라 같은 DB의 행 저장이므로, 이 격리가 필요한 정책인지 재확인할 가치가 있다.

같은 트랜잭션에 저장하면 알림 전용 대기열과 폐기 체계가 줄지만, 알림 저장 실패·시간을 본 요청이 부담한다. 격리를 유지하면 알림 유실 가능성을 받아들여야 한다. outbox나 메시지 브로커를 자동으로 추가하자는 제안이 아니다.

현재 구조의 대가는 단순 지연만이 아니다. 포화·프로세스 종료·저장 실패로 유실될 수 있고, DB 자원을 공유하므로 본 기능의 성능 영향까지 없어지지는 않는다.

### 5-2. 정상 중복을 ORM 예외로 판별한다

`NotificationService.notify()`는 중복 INSERT를 실패시킨 뒤 Hibernate 예외와 제약 이름을 검사한다. 중복이면 기존 행을 변경하지 않는 저장소 SQL과 비교할 수 있다. 대가는 MySQL 전용 SQL 및 명시적 INSERT 관리다. 다른 제약 위반까지 덮는 `INSERT IGNORE`는 제안하지 않는다.

### 5-3. 탈퇴한 행위자의 알림 목록 실패

알림은 남아 있지만 `findActorViews()`는 탈퇴자를 제외하고, `NotificationResponse.of()`는 `actor`가 있다고 가정해 역참조한다. 해당 알림이 페이지에 포함되면 null 참조 오류가 가능하다.

탈퇴자 알림을 숨길지, 행위자 정보 없이 남길지 결정해야 한다. 숨긴다면 목록과 안 읽은 개수에 같은 기준을 적용해야 한다. 목록에서만 사후 필터링하면 페이지와 배지가 어긋난다.

**근거 코드:** `notification/NotificationService.java`, `notification/NotificationListener.java`, `notification/NotificationOverflow.java`, `notification/dto/NotificationResponse.java`, `common/config/AsyncConfig.java`.

## 6. 탈퇴 계정의 보존 범위와 작업 허용

**대상:** `user` 및 인증·쓰기 경로 / **구분:** 정책 결정 + 오류 경로

현재 탈퇴는 시각만 설정하며 이메일·비밀번호 해시·프로필 등은 남긴다. 이 선택 때문에 활성 계정용 생성 컬럼, 조회별 탈퇴 제외, 남은 토큰 처리, 추후 파기 작업이 필요하다.

`CLAUDE.md`에 보존 정책이 명시돼 있으므로 임의로 삭제할 수 없다. 재검토할 질문은 “과거 콘텐츠와 운영 기록을 남기는 데 로그인 정보와 프로필까지 원형 그대로 필요한가”다. 참조용 ID·프로필·로그인 정보의 보존 목적을 나눠 판단해야 한다. 법적 적합성을 검토한 문서는 아니다.

또한 글·댓글 작성은 탈퇴자를 거부하지만 `UserService.updateProfile()`은 `findById()`만 사용한다. 남은 access 토큰으로 탈퇴 행의 프로필을 수정할 수 있는 경로다.

로그아웃 후 토큰 잔존과 탈퇴 계정의 작업 허용을 같은 정책으로 취급하지 않아야 한다. 작업마다 임시 검사를 추가하기 전에 차단 범위와 공통 적용 지점을 결정한다. 모든 요청에 DB 조회를 추가하자는 확정 제안은 아니다.

## 7. 범위가 작은 단순화 후보

| 대상 | 현재 전제·처리 | 검토할 대안과 주의점 |
|---|---|---|
| book / `BookInserter` | 저장 실패 격리를 위해 별도 `REQUIRES_NEW` 빈 유지 | 현재 `upsert()`에는 외부 트랜잭션이 없고 운영 호출자는 컨트롤러다. 저장소 자체 트랜잭션 경계로 충분한지 기존 중복 등록 테스트로 검증하고 위임 빈 제거. 향후 외부 트랜잭션 호출은 별도 검토 |
| book / `Canonical.normalized` | 정규식 이스케이프 실수를 피하려 직접 문자 순회 구현 | 올바른 사전 컴파일 패턴과 테스트로 줄일 후보. NBSP 등 기존 공백 처리와 NFC 의미를 보존해야 함. 현재 성능 오류라는 지적은 아님 |
| feed / 팔로잉 ID 전체 전달 | 관계를 DB에서 전부 읽고 애플리케이션을 거쳐 다시 IN 조건으로 전달 | 글 조회 안에서 EXISTS/NOT EXISTS로 판정. 목록 조립·빈 목록 분기를 줄일 수 있으나 DB 실행 시간 개선은 실행 계획과 측정으로 확인 |
| follow / 목록 조립 | Follow 조회 후 User 전체 조회와 Map 조립 | 관계 ID와 표시용 사용자 값을 직접 조회하는 타입과 비교. 기존 일괄 조회도 합리적이며 강제 변경 대상은 아님 |
| post / 댓글 정렬 | 공통 커서 방향을 맞추려고 최신순 채택 | 최신순은 제품 정책으로 판단. 페이지별 뒤집기는 전체 오래된 순서를 보장하지 않음 |

### 추가로 과장된 보장 정리

- ISBN 없는 책의 제목·저자·출판사 해시는 근사 식별이다. 같은 책의 표기 변경이나 다른 판본을 완벽히 구분하지 못한다. 해시 알고리즘이 이 의미상의 문제를 해결하지 않는다.
- 홈과 팔로잉 피드가 겹치지 않는다는 것은 같은 팔로우 상태 기준이다. 두 요청 사이 팔로우가 바뀌면 결과를 합쳤을 때 중복될 수 있다. 바로 스냅샷 장치를 추가하기보다 보장 범위를 정확히 적는다.
- `Reading`의 “책마다 한 행”, `FollowService`의 “복합 PK”, `User.updateProfile()`의 “전체 UPDATE” 등 과거 구현 설명이 남아 있다. 현재 동작과 일치시켜 후속 판단의 잘못된 근거가 되지 않게 한다.

## 유지해야 할 보장

단순화 작업에서 다음을 함께 삭제하지 않는다.

- 유니크 제약에 의한 중복 관계 방지.
- 권한·소유자·탈퇴 여부 등 실제 접근 정책.
- 작성자 삭제와 운영자 숨김의 구분.
- 상태·총 쪽수·진도처럼 결합된 값의 동시성 보호.
- 공용 책 메타데이터 변조 방지. HMAC을 없애려면 서버 재조회 등 대안이 필요하다.
- `ReadingInserter`의 경우 실제 외부 트랜잭션이 있으므로 `BookInserter`와 동일하게 삭제하지 않는다.
- 알림·팔로워 수의 직접 COUNT, 연간 목표의 단일 SQL upsert처럼 이미 보정 복잡성을 줄이는 구현.

## 권장 진행 순서와 완료 기준

- [ ] 정책 결정: 반응 수 저장 필요성, 신고 판단과 복구의 관계, 독서 회차·실적 기준, 자동 담기, 알림 실패 허용, 탈퇴 보존·작업 허용 범위를 각각 분리해 결정한다.
- [ ] 오류 검증: 다중 신고 동시 기각, 탈퇴 행위자 알림 조회, 상태·쪽수 동시 변경, 탈퇴 후 프로필 수정 경로를 테스트로 확인한다.
- [ ] 원인 제거: 합의한 전제를 바꾸면서 파생된 보정·위임·분기를 함께 제거한다. 현재 보장을 유지해야 하는 오류는 결정 대기 중에도 방치하지 않는다.
- [ ] 데이터 전환: 기존 배포 이력을 확인하고 새 마이그레이션과 호환 계획을 만든다. 적용된 마이그레이션을 임의로 되돌리지 않는다.
- [ ] 회귀 검증: 공개 응답, 권한, 삭제·숨김·복구, 동시 생성·삭제, 재가입, 과거 독서 기록을 검증한다.
- [ ] 성능 검증: 페이지 단위 집계와 관계 조회의 쿼리 수·실행 계획·지연을 실제 데이터로 비교한다. “쿼리가 줄었다”와 “항상 빨라졌다”를 혼동하지 않는다.
- [ ] 문서 정리: 현재 요구, 구현 선택, 허용하는 실패를 구분해 기록한다. 이전 구현을 정당화하던 주석을 제거한다.

완료의 기준은 줄 수 감소가 아니라, **동일하게 필요한 보장을 지키면서 유지해야 할 상태와 보정 규칙이 줄었는가**다.
